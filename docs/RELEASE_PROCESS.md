# Release process

This process separates a technically valid candidate from authority to publish it.

1. Before selecting public visibility, explicitly accept the GitHub Terms public-content/fork and service-operation, improvement, and AI/ML-training rights that apply to a public repository. Then record repository visibility, the all-rights-reserved no-additional-license root notice, included projects, provenance attestations, public Git identity, review owner, conduct/security channel, public-data distribution decision, and hero approvals in `release-decisions.json`.
2. Recheck the sealed source inventory and redaction/data-license receipts. Do not refresh hashes merely to silence drift.
3. Export into a new empty directory through the default-deny map. Never copy a whole working tree and delete files afterward.
4. Run policy, inventory, links, generated-output, unit, browser, mobile-overflow, privacy, and manifest checks. Inspect every hero at native resolution.
5. Confirm the exact file list excludes private reviews, local paths, caches, old manifests, legacy screenshots/mockups, and nested repositories; confirm public-data paths match `THIRD_PARTY_NOTICES.md`.
6. Only after identity, license-notice, and GitHub Terms rights approval, initialize a new local `main` repository and make the first commit.
7. Clone that local repository with `--no-local` into another empty directory. Verify the manifest before and after execution, run the complete matrix, and require an empty status plus no cache artifacts.
8. Record commit, tree, manifest, dependency, test, browser, public-data receipt, and visual-review hashes.
9. Require an exact-current independent external review of the clean clone covering rendered presentation, privacy, restrictive licensing and third-party rights, claims, brand/off-color hygiene, and professionalism. Bind every finding to exact bytes, adjudicate it, and rerun every affected deterministic check. The private promotion controls select the approved review service; public candidate bytes remain provider-neutral. This is a pre-remote hard gate, not publication authority.
10. Stop for distinct remote and publication authorizations. After remote creation, require a settings receipt proving Issues and pull requests are disabled, no outside account has write access, private vulnerability reporting is enabled, and Pages/release automation remain off. The pre-remote candidate records only intended settings, not observed settings.
11. After an authorized push, clone the remote at the exact commit and repeat policy, manifest, unit, browser, and data-receipt checks.

Failure at any step returns the release to hold. The release manifest is an integrity receipt, not a signature or trusted timestamp.

Network proof is layered rather than inferred from every URL-shaped JavaScript string. The root literal scan covers HTML and CSS automatic-load surfaces; project scans reject `fetch`, XHR, WebSocket, beacon, storage, and related runtime primitives; link verification constrains user-initiated external destinations; and real-browser checks require zero automatic HTTP(S) requests. JavaScript URL strings may therefore represent frozen evidence or explicit user-click links without being mislabeled as network execution.
